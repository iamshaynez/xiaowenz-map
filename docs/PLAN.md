## Context

你要一座 pixel-plays 风格的像素杭州：以主城区为主，同样的像素味，可以旋转、缩放、从不同角度和远近观看。前两轮讨论已经定下来的事：

- **范围**：主城区。其余市域不做。
- **形态**：活的像素地图。有船、车、人、风，有地标名录和导览镜头，没有任务和数值。
- **设备**：桌面优先，手机可用。
- **缺失数据**：先找真实数据，不够再推测，并标明哪些是推测。
- **季节**：四季可切换。
- **视角**：连续旋转的轴测相机。上一轮用原版引擎做的实验已证明场景可以转。

这份计划按"一次性完成"来写：你批准之后我不再提问，所有决定写进 `docs/DECISIONS.md`，需要你品味判断的问题先按最合理的方案做并记入 `docs/REVIEW-QUEUE.md`，最后一并交给你。只有三道闸门不过时我才会停下来找你。

**调研已确认的事**
- pixel-plays 代码是 MIT 许可。它的做法是"世界空间的真实几何 + 屏幕空间的上色规则"，所以几何可以转。但 CPU 每换一次视角要重烘 35–48 毫秒，转整座城必须改用显卡。
- OpenStreetMap 在老城区的建筑轮廓很好（每平方公里 50–310 栋），楼高几乎没有标注；外围城区每平方公里只有 12–57 栋。
- Geofabrik 提供浙江省的单独提取包（87 MB）。
- 楼高有候选的开放数据：3D-GloBFP（2024 年发表，CC BY 4.0，2020 年数据，在中国的误差约 13 米）。备用是 CNBH-10m，获取条件未知。
- 地形有候选：Copernicus GLO-30（覆盖全区的一块 48 MB）和 Terrarium 高程瓦片。
- 这台机器是 Mac Studio，Chrome 157，Node 24，Python 3.14（有 numpy，没有地理库），磁盘余 1.8 TB。

**没能验证的事**（计划模式下不能执行命令，列为第一阶段最先做的事）：Zenodo 和 AWS 从本机的可达性与速度；显卡的 WebGL2 吞吐；显卡版与原版的观感是否一致；主城区建筑总数；3D-GloBFP 是否覆盖杭州。

## 目标与完成的定义

范围是东经 120.00–120.40、北纬 30.12–30.44，约 38.5 km × 35.6 km，包含西湖及西湖群山、西溪、运河、钱江新城、奥体、下沙、未来科技城。整座主城区做成一个悬浮在白底上的立体模型，边缘按 pixel-plays 的方式用抖动散点溶进白色。

这一轮结束时应当满足：
- 运行 `node serve.mjs` 打开页面，5 秒内看到整座主城区。
- 能连续旋转、俯仰、缩放（三四百倍）、平移，本机桌面浏览器 60 帧。
- 四季一键切换；24 处地标一键飞达；西湖十景导览可播放。
- 每栋楼、每条路、每片水都来自真实数据，或在文档和调试图层里标明是推测。
- 自动测试全部通过；附一套 40–60 张的验收图供你过目。

## 架构

**目录**：`app/`（网页）、`pipeline/`（Python 数据管线）、`data/`（raw、baked 不入库，curated 入库）、`tools/`、`tests/`、`docs/`，根目录放 `serve.mjs`。

**数据管线**把原始数据整理成 1 公里见方的二进制瓦片（`data/baked/`），网页按需加载。图层包括地形网格、水面、道路、铁路、建筑、树、土地利用、标注。

**楼高按这个顺序取值**，并记录来源：
1. 人工核对的地标表（`data/curated/landmarks.json`）。
2. OSM 自带的 height。
3. OSM 的 building:levels 乘 3 米。
4. 3D-GloBFP 里能匹配上的建筑。
5. 推断：按建筑类型、名称关键词（大厦、公寓、苑、村等）和轮廓形状估层数。

**缺失建筑按这个顺序补**：先看 3D-GloBFP 在该处有没有真实轮廓；没有才用程序生成的典型楼群（成排的板楼、小区、厂房），并标记为推测。

**渲染分四档**，按"每米多少像素"切换：

| 档 | 1 像素 | 能看到 | 做法 |
|---|---|---|---|
| 全景 | 8 米以上 | 山、水、主路、整片楼群 | 合并的体块，无阴影无树 |
| 城区 | 1–8 米 | 每栋楼带屋顶、每条路、树丛 | 轮廓挤出，阴影开 |
| 街区 | 0.2–1 米 | 立面的窗和阳台、街道设施、树形、车形 | 着色器里的程序化细节 |
| 小景 | 0.2 米以下 | 人物、栏杆、船 | 人物骨架，只在近处 |

**样式引擎**：把 pixel-plays 的上色规则逐条移植到显卡上。原文件是 `reference/pixel-plays/engine.js`。

| 原版 | 位置 | 移植方式 |
|---|---|---|
| 五级色阶，暗部偏紫亮部偏暖 | `rampOf` | 着色器函数，规则不变 |
| 球体光照与抖动 | `sphere` | 改为世界空间的法线光照，默认机位下数值与原版一致 |
| 长方体三个面的亮度 | `box` | 按面的朝向取向阳度 |
| 阴影只落在地面和水面 | `castShadow` `applyShadows` | 阴影贴图，只给地面和水染色 |
| 深度描边与暖色边光 | `shadeEdges` | 后处理，直接移植 |
| 环境光遮蔽 | `bakeOcclusion` | 后处理，16 点采样，直接移植 |
| 树与草每秒 8 帧的步进摆动 | `drawTufts` `drawLeaves` | 顶点着色器，时间量化，位移取整到整像素 |
| 人物 | `figure` | 胶囊网格，不抖动的平涂色带 |

为了保住原版线条偏粗的手感，场景先按 2×2 超采样绘制，只要有一个采样点被盖到就保留该像素。是否需要由观感闸门来定。

**季节**：所有颜色必须经过一张集中的调色板表，每个季节一套。香樟四季常绿；柳、梧桐、桃、樱、梅、桂、荷按季节换色或显隐；冬季在朝上的面上叠一层抖动的雪。

## 验证

**三道闸门**（第一阶段）：
- **观感一致**（不过则停）：显卡版与 CPU 参照版在同一场景、四个机位下对比。轮廓重合度 ≥ 97%，描边像素吻合 ≥ 90%，3×3 均值模糊后的颜色差 ≤ 10/255，明暗档位的分布差 ≤ 2%。另附并排对照图给你看。
- **吞吐**（调优两轮仍不过则停）：本机真实显卡上，全景档内部分辨率 960×540 不低于 60 帧，街区与小景档 640×400 不低于 60 帧，95% 的帧 ≤ 20 毫秒。
- **数据充足**（只在地图建不起来时才停）：主城区建筑 ≥ 10 万栋；地形加载成功；西湖水面约 6.4 平方公里。楼高里非推断的占比作为指标写进数据报告，不达标不停工，改走推断退路。

**持续验证**：
- 数据管线的单元测试；渲染器的金标回归（上表的对比指标每次改动后重跑）。
- Playwright 脚本：加载无报错、四季切换、24 处地标逐一飞达、旋转缩放平移、手机触控模拟。
- 10 分钟随机漫游：无报错、无显卡上下文丢失、内存无明显增长。
- 验收图：每处地标 3 个角度；西湖核心四季各一张；从全景拉到断桥的 5 个缩放档；一圈旋转扫视。

## 风险与退路

| 风险 | 退路 |
|---|---|
| 显卡版观感不过关 | 调超采样倍数、覆盖判定、抖动偏移，各试一轮。仍不过就停下报告，不在一套不像的渲染器上盖整座城 |
| 3D-GloBFP 下不动或没有杭州的瓦片 | 改用 CNBH-10m；再不行用推断，并在数据报告里写明推断占比 |
| 弱显卡跑不动 | 像素大小可调；手机降档；远景合并体块 |
| OSM 几何脏（碎片、重叠、重复） | 清理规则：最小面积、去重、简化容差 |
| 地标形似度有限 | 我只能依据文字资料和轮廓数据建模，没有照片参照。形似度留给你看过验收图后再提 |
| 运行中断 | 每阶段提交并更新 `PROGRESS.md`，下次从断点继续 |

## 你需要知道的

- **我看不了图。** 这个环境里截图只能交给视觉模型转述，而且它时常解析失败。所以画质靠客观指标、测试和验收图来保证，最终的审美判断需要你来看验收图。
- **这会是很长的一次运行**，我没法给出可靠的耗时。七个阶段里每个阶段结束都有一个能打开的版本。
- **运行中会做的事**：下载约 0.3–2 GB 开放数据；在项目里建 Python 虚拟环境并安装几个包；初始化 git 并本地提交；测试时会启动浏览器，测真实显卡性能时可能弹出窗口。不推送、不部署、不发布。
- **外围会是近似的。** 老城区最准；萧山市北、下沙、九堡、闲林一带的建筑，以及全城的楼高，有相当一部分来自开放数据集或推断。哪些是推测会写进数据报告，也可以在页面里打开调试图层查看。
- **浏览器只保证 Chrome。** Safari 和 Firefox 尽力做冒烟测试，做不了会写进已知问题。
